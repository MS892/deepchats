## Fragestellung

Welcher Architektur-Stil soll für das deepchats-System verwendet werden?
Das System muss:
- Unterschiedliche Chat-Typen (Aktion, Wissen, Meta) unterstützen
- Intuitiv erweiterbar sein (neue Typen, Fragen, Post-Processoren)
- Als CLI-Tool auf Windows (Git-Bash) laufen
- SQLite, Memory-KG, GitHub MCP integrieren
- Von einem einzigen Entwickler gewartet werden

## Decision Tree

```
START: Architektur-Stil wählen
│
├─[Frage 1] Muss das System als verteilter Dienst laufen?
│  ├─ JA → Microservices / Service-Oriented
│  │       └─ ABGELEHNT: Overhead für Einzelentwickler,
│  │          keine Verteilungsanforderung
│  └─ NEIN → Monolithisch oder Modular
│
├─[Frage 2] Müssen Chat-Typen unabhängig voneinander
│           deployt/aktualisiert werden können?
│  ├─ JA → Plugin-Architektur mit Dynamic Loading
│  └─ NEIN → Statische Module innerhalb eines Monolithen
│             └─ ABGELEHNT: Erweiterbarkeit ist Kernanforderung
│
├─[Frage 3] Soll die Erweiterung ohne Änderung des
│           Core-Codes möglich sein?
│  ├─ JA → Plugin/Registry-Pattern notwendig
│  │       └─ GEWÄHLT: Modular Monolith + Plugin-Registry
│  └─ NEIN → Einfacher Monolith
│
└─[Frage 4] Wie werden Plugins registriert?
   ├─ Dateisystem-Discovery (importlib)
   ├─ Deklarative Registrierung (setup.py entry_points)
   ├─ Manuelle Registrierung (registry.register())
   └─ GEWÄHLT: Kombination aus Dateisystem-Discovery
      + manueller Registrierung
```

## Entscheidung

**Modularer Monolith mit Plugin-Registry-Pattern**

### Begründung

1. **Einfachheit:** Ein Prozess, eine Installation, minimale operative Komplexität
2. **Erweiterbarkeit:** Neue Chat-Typen werden als Python-Module in `app/chat_types/` abgelegt und via importlib automatisch entdeckt
3. **Testbarkeit:** Alle Module können gemeinsam getestet werden
4. **MCP-Kompatibilität:** SQLite und Memory-KG sind als Embedded-Systeme ohnehin lokal
5. **Wartbarkeit:** Eine Codebase, klare Modulgrenzen, Type-Hints

## Alternativen (verworfen)

| Alternative | Grund der Ablehnung |
|-------------|---------------------|
| Microservices | Overhead, keine Verteilungsanforderung, Dev-Ops-Komplexität |
| Reiner Monolith ohne Plugins | Erweiterbarkeit nicht gegeben, jede Änderung am Core nötig |
| YAML/JSON-Konfiguration statt Code-Plugins | Limitierte Logik-Möglichkeiten, keine echten Post-Processoren möglich |
| Rust/Go für Performance | Schnellere Iteration mit Python wichtiger, kein Performance-Engpass |

## Konsequenzen

- **Positiv:** Neue Chat-Typen = neue Datei in `chat_types/`, keine Core-Änderung
- **Positiv:** Neue Post-Processoren = neue Datei in `post_processors/`
- **Negativ:** Keine isolierte Skalierung einzelner Komponenten (nicht benötigt)
- **Negativ:** Python-Abhängigkeit für alle Plugins

## Validierung

- [ ] Neuer Chat-Typ kann in < 5 Minuten hinzugefügt werden
- [ ] Plugin-Discovery funktioniert ohne manuelle Registrierung
- [ ] Alle bestehenden Tests laufen nach Plugin-Hinzufügung weiter
